# dsh-maa-cli

[![npm](https://img.shields.io/npm/v/dsh-maa-cli.svg)](https://www.npmjs.com/package/dsh-maa-cli)
[![license](https://img.shields.io/npm/l/dsh-maa-cli.svg)](LICENSE)
[![node](https://img.shields.io/badge/node-%3E%3D22-brightgreen)](https://nodejs.org)
[![Listed on dsh-plugin.org](https://dsh-plugin.org/badges/listed.svg)](https://dsh-plugin.org/plugins/nhyo/dsh-maa-cli)

一个 [DeepSeek Harness](https://github.com/deepseek-ai/deepseek-harness) 插件：把《明日方舟》的日常操作变成一条本地命令，复杂需求才交给模型组装计划。

- **日常操作零模型调用**：只输入 `/maa fight`、`/maa infrast`、`/maa rouge` 等项目名即可打开参数面板；修改并确认后才执行，全程不进入模型上下文。
- **确认与执行分离**：自然语言需求只消耗一次模型调用生成计划，执行由本地确认按钮触发，确认阶段不再调用模型。
- **不需要预装 MAA**：插件自带私有运行时，首次真正执行任务时自动下载 maa-cli + MaaCore + 资源，与系统里已有的 MAA 完全隔离。
- **运行中可交互**：任务在后台执行时仍可查询真实进度、立即停止，或设置“本局结束后 / 再打 N 局 / 指定层 Boss 前停止”；只控制本插件当前任务的 maa-cli 进程树，不动游戏、模拟器或其它 MAA 实例。
- **按需自动更新**：开始新任务前至多每 24 小时调用一次 maa-cli 官方更新；培养榜只在用户请求建议时检查。

## 快速开始

```text
dsh plugin --profile desktop add dsh-maa-cli
```
或
```text
dsh plugin --profile web add dsh-maa-cli
```
安装完成后**重启 DSH Desktop**，然后任选一种方式：

```text
/maa fight              # 打开理智作战参数面板，不会立即开打
/maa update             # 选择更新干员 Box / 仓库数据
/maa setup              # 想提前下载运行时的话
```

第一次真正执行游戏任务时会自动准备私有运行时（约 520–630 MB，视网络通常 1–3 分钟）。任务开始前请确保模拟器已经启动；没启动时插件会直接提示「请手动启动mumu模拟器！」，不会消耗理智，计划也不会失效。

## 本地命令（零模型调用）

命令走 DSH 的本地命令通道，**完全不产生模型调用**。任务命令只负责打开面板；不点击「确认并执行 MAA」就不会操作游戏。

| 命令 | 别名 | 作用 |
| --- | --- | --- |
| `/maa help` | `帮助`、`?` | 显示命令帮助 |
| `/maa startup` | `启动游戏`、`打开明日方舟` | 打开开始唤醒面板 |
| `/maa fight` | `flight`、`刷`、`作战` | 打开理智作战面板 |
| `/maa infrast` | `基建`、`基建换班` | 打开基建换班面板 |
| `/maa recruit` | `公招`、`自动公招` | 打开自动公招面板 |
| `/maa mall` | `credit`、`信用收支` | 打开信用收支面板 |
| `/maa award` | `领取奖励`、`领奖` | 打开领取奖励面板 |
| `/maa rouge` | `rogue`、`roguelike`、`肉鸽` | 打开自动肉鸽面板 |
| `/maa reclamation` | `生息`、`生息演算` | 打开生息演算面板 |
| `/maa update` | `更新数据` | 选择更新干员 Box / 仓库数据 |
| `/maa closedown` | `关闭游戏`、`关闭明日方舟` | 打开关闭游戏确认面板 |
| `/maa box` | `operbox`、`扫描干员Box` | 打开只更新干员 Box 的数据面板 |
| `/maa stop` | `停止`、`停止任务`、`终止任务` | 停止正在执行的任务，并清理 DSH 重启后残留的 maa-cli 进程 |
| `/maa status` | `状态`、`任务状态`、`执行状态` | 面板内部使用：读取执行中的任务与最近几次执行记录 |
| `/maa 这把肉鸽打完就停` | `本局探索打完后停` | 收到可靠的肉鸽结算回调后停止，不开启下一局 |
| `/maa 再打两局就停` | — | 从当前可靠进度起，再收到两次探索结算后停止 |
| `/maa 第五层 Boss 前停止` | — | 仅在 MAA 明确报告 `StageDreadfulFoe-5` 时于进入 Boss 战前停止 |
| `/maa 取消刚才的停止要求` | `撤销停止条件` | 取消尚未触发的条件停止；已经触发的终止不能撤回 |
| `/maa 现在打到哪里了` | `查看实时进度` | 返回日志已确认的局数、楼层、关卡和运行时指令状态；未知值不会猜测 |
| `/maa setup` | `安装运行时`、`初始化` | 下载并配置私有运行时 |
| `/maa confirm MAA-XXXXXX [参数]` | — | 面板内部确认命令；通常不需要手工输入 |

示例：

```text
/maa fight              # 在面板里选关卡、次数、连战倍率与资源上限
/maa infrast            # 在面板里选设施、无人机用途、心情阈值等
/maa recruit            # 在面板里选择刷新、星级、次数与加急许可
/maa mall               # 在面板里选择访问好友、购物与名单
/maa rouge              # 在面板里选择主题、模式、分队与开局干员
/maa update             # 在面板里选择 Box、仓库或两者
```

约定：

- 所有面板参数来自同一套服务端白名单，确认前会再次校验；非法参数不会消耗确认码。
- 参数布局和字段类型遵循 MAA 官方任务协议；可发现的主题、模式、难度、分队、干员等选项及默认值以当前实际运行的 MAA 版本和资源为准。
- 兼容旧写法（如 `/maa fight 1-7 10`、`/maa rouge 萨米 3`），但旧参数只用于预填面板，仍不会直接执行。
- 执行期间确认条会显示「停止任务」「本局结束后停」「取消停止条件」「查看实时进度」。MaaCore 没有可靠的暂停/继续接口，因此停止后不会自动补完剩余局数。
- 确认之后面板不会消失：它切换成运行控制面板，显示「执行中 / 已完成 / 失败 / 已停止」、耗时、可靠进度与退出码，并保留「停止任务」「本局结束后停」「取消停止条件」「查看实时进度」。计时在本地完成，不会反复调用命令；记录写在主机的 `runs.json` 里，刷新页面、切到别的会话、甚至重启 DSH 之后都还能看到最近一次执行。
- 确认后的 MAA 进程由插件在后台持有，`/maa confirm` 会立刻返回「已开始执行（RUN-…）」而不再占着一次命令调用：这样长任务不会被命令传输的 5 分钟超时打断。运行结果、资源覆盖恢复与 `runs.json` 都在进程真正退出时结算。
- 有任务正在执行时，插件拒绝一切新计划与确认（`maa_prepare_*` 工具与 `/maa confirm` 都会明确报错），避免抢占模拟器和覆盖临时资源；所有 DSH 会话共享这一限制。`/maa stop` 在 DSH 重启后也能清理残留的 `maa-cli` 进程。

### 运行时指令

确认后的 MAA 子进程不会占住 DSH 命令通道，因此执行期间仍可在对话中追加运行时指令。插件把每条指令持久化在本次 `runs.json` 记录中，并严格区分 `received`（已接收）、`applied`（已挂载到当前监控器）、`triggered`（可靠条件已发生并开始终止）、`completed`（触发后的 MAA 进程已结束）、`not_triggered`（进程先结束、条件没有发生）、`cancelled` 和 `unsupported`。新的停止条件会取消旧的尚未触发条件；临时指令不进入长期策略记忆。

局数只根据 MaaCore 的 `RoguelikeSettlement` 回调累加；黑流树海楼层只接受带 `floor_from_ocr: true` 的 `BlackFlowMapSummary`；指定层 Boss 只接受精确的 `StageDreadfulFoe-<层数>` 预进入回调。日志没有可靠字段时，状态会显示“未知”并继续等待，不按耗时或文本猜测，也不会错误停止。

MaaCore 原生的 `AsstSetTaskParams` 需要调用方持有同一进程内的 Assistant 句柄和 task id；本插件当前通过独立 `maa-cli run` 子进程执行，maa-cli 没有把这些对象暴露给 DSH。因此“接下来优先招某干员”会明确记录为 `unsupported / 未应用`，不会靠运行中改资源文件冒充已经生效；请把它放到下一次任务的备注中，经预览确认后执行。

### 统一零模型参数面板

截图中的 MAA 主任务已全部接入同一流程：开始唤醒、理智作战、基建换班、自动公招、信用收支、领取奖励、自动肉鸽、生息演算、更新数据。输入 `/maa + 项目名` 后，插件在输入框上方显示对应面板；参数改动、只读回读和确认全部走本地命令通道。

```text
/maa fight
/maa recruit
/maa mall
/maa rouge
/maa reclamation
/maa update
```

- 基础项直接显示，高级项放在「高级设置」中；布尔项使用复选框，枚举使用下拉框，多选项使用复选框组，数量使用受范围限制的数字框。
- MAA.exe 原本带提示的设置会在对应字段下显示说明；生息演算会根据当前模式显示启动位置、存档/编队要求、所需干员、预期流程和注意事项。
- 肉鸽保留专用面板和 MAA 推荐开局；其他项目使用统一表单渲染器。
- “更新数据”对应 MAA 的 `UserDataUpdateTask`：可分别选择 `OperBox` 与 `Depot`，不会被误解为下载软件更新。
- 面板里的参数来自待确认计划本身（`/maa peek` 只读回读），打开时看到的就是将要执行的值。
- 下拉框显示值和确认时提交值使用同一套规范化规则。MAA 能力缓存刷新、主题切换或上游删除选项后，失效值会自动换成当前合法默认值；没有可靠默认值的可选项显示为“未选择”。
- 未选择的可选文本、列表和下拉项不会以空字符串写入 MaaCore；如果用户把原有值改回“未选择”，对应参数会从最终任务中删除。必填项缺失则在消费确认码前报出具体字段，不会执行任务。
- 不点确认就什么都不会执行；计划 30 分钟有效、一次性，`/maa confirm MAA-XXXXXX …` 也能手动执行。
- `/maa peek MAA-XXXXXX` 是面板用的只读命令，手工用只会打印计划的 JSON，不会执行。
### 干员 Box 查询

`/maa box` 会先打开只包含 `OperBox` 的确认面板；确认后才识别已拥有干员并保存到 `~/.dsh/maa-cli/operator-box.json`。缓存只包含干员 ID、名称、星级、精英化、等级、潜能和扫描时间，不包含账号凭据。

扫描一次后，可以直接用自然语言询问：

```text
我有哪些六星干员？
哪些六星还没精二？
维什戴尔多少级、几潜？
给我一份培养建议
```

DSH 会先调用只读的 `maa_operator_box` 查询缓存，不连接模拟器。没有缓存，或用户明确要求刷新时，才会准备一份需要确认的 `StartUp + OperBox` 扫描计划。

每次扫描完成后，插件会主动询问是否需要培养建议。用户主动询问时，DSH 会先显示上次扫描时间，并让用户选择直接使用缓存还是重新扫描；重新扫描仍需单独确认。

培养建议使用以下可审计规则：

- 这是蒂蒂，她很可爱！！！
- 杯级来自[明日方舟六星干员强度投票箱](https://vote.ltsc.vip)最新已发布主题，按该项目原有的九等分规则归为 `超大上 > 超大中 > 超大下 > 大杯 > 中杯 > 其他`。这是社区投票，不是官方强度结论。
- 职业与子职业读取当前 MAA 运行时自带的 `battle_data.json`，不维护另一份容易过期的名单；职业内排名由同一社区总榜按职业分组得到。
- “已有可用职业覆盖”定义为该职业至少有一名精一或精二干员。没有时会提高该职业候选人在同杯级内的顺序，并明确写出职业缺口原因。
- 只推荐尚未精二、或精二但低于 60 级的已拥有六星；榜单没有收录的干员标为“其他”，不会补造评级或排名。
- 每次生成建议前只检查最新已结束主题 ID；主题未变化时直接复用 `~/.dsh/maa-cli/training-ranking.json`，不重复下载完整榜单。新主题下载成功后才原子替换；检查失败则继续使用旧缓存。


## 自然语言用法

复杂需求仍然可以直接说，例如「先启动游戏，清一下基建，再刷十次 1-7，最后领奖励」。

1. 模型调用一次 `maa_prepare_plan`，把需求整理成有顺序的步骤，写入任务文件并**落盘保存**。
2. DSH 输入框附近出现确认条（思考区的工具卡里也有同样的按钮）。确认条右上角有「最小化 / 删除」：最小化把它收成一行摘要并保留确认按钮以外的全部状态（展开后参数还在），删除则让这一条计划从当前界面消失（工具卡上的确认按钮同步隐藏），确认码本身仍可用 `/maa confirm <code>` 手动执行。
3. 若填写备注，离开备注栏时会自动解析（也可点击「解析并预览备注」）：插件优先用本地规则和已启用策略记忆编译；只有语义无法确定时，才把未识别部分交给模型重新准备策略——模型会先识别主语（干员/藏品/事件名，纠正错别字）和动词（抓、拿、捞、取、选、选择、招募都按「招募」理解），改写成规范化备注后调用 `maa_prepare_note`，再由本地规则重新解析和编译。参数或备注变化后旧预览自动失效。
4. 备注解析成功后，面板只提示「已收到并解析【备注】」（识别细节保留在命令结果里由模型说明）。点击「确认并执行 MAA」→ 本地执行 `/maa confirm <code>` → 临时应用策略并运行 maa-cli；未完成备注预览时不能确认。

### 自然语言策略编译

需要改变肉鸽策略或战斗作业时，DSH 会调用 `maa_prepare_strategy`（备注场景调用 `maa_prepare_note`），把自由表达和多意图组合编译成 MAA 原生资源或 Copilot 作业，再沿用同一套确认码执行。它不是只保存“意图 JSON”：确认后会把策略真正写入本次执行读取的资源/作业文件。

肉鸽战术直接写进 `roguelike/<主题>/autopilot/<关卡>.json` 的原生 `deploy_plan`（保留 `replacement_home` 等既有字段），并按文件内的 `stage_name` 查找关卡，因此和 MAA 自带的自动战斗共用同一套机制。备注里不写关卡名时，默认对该主题**全部原生 autopilot 关卡**生效：插件读取 `Arknights-Tile-Pos` 地图数据，按干员的 `position`（地面 / 高台）沿入口到蓝门的路径自动选点并计算朝向，所以不需要用户或模型手填坐标。显式点名关卡时才使用给出的坐标与朝向；点名了关卡却缺坐标、朝向，或主题没有该关卡 autopilot 配置时，会逐条列入“无法执行并给出原因”，没有地图数据的关卡也会列出名字，不会静默丢弃，也不会伪造资源条目。招募策略的覆盖文件是“内置分组 + 新增分组”的完整副本，因为 MAA 会整体替换该主题的招募表。

支持的原生能力：

- 按肉鸽主题调整指定干员的招募优先级、技能和精二优先级；招募表缺少该干员时，用 `battle_data.json` 校验干员真实存在后，新增最小合法分组（`skill`、`is_key`、`is_start`、`recruit_priority`、`promote_priority`），查不到干员则明确拒绝；
- 用主题已有的原生分组重设 `team_complete_condition`；
- 将指定藏品移到购买队列前部，或从购买队列移除；
- 按肉鸽模式选择对应事件策略文件，并修改已收录事件的优先选项；
- 切换主题后只修改该主题的 `recruitment.json`、`shopping.json` 和事件策略；
- 生成 Copilot 的有序部署、技能、撤退、技能用法等动作，支持 `[x, y]`、方向、费用、延迟和击杀数条件；
- 对“堵门”“守蓝门”，在肉鸽主题的 `autopilot/<关卡>.json` 里追加 `deploy_plan` 条目：不写关卡名时对该主题全部原生关卡自动选点（按 `position` 区分地面/高台、沿路线朝入口方向），点名关卡时使用给定坐标；Copilot 场景则从 `Arknights-Tile-Pos` 的可通行格估算入口到蓝门的最短路径，选择靠近目标的可部署格；
- 同一请求可以同时包含多名干员优先级、阵容条件、藏品、事件或多条战斗动作。

安全与回退：

- 肉鸽策略通过 maa-cli 官方 `--user-resource` 从配置目录覆盖加载，MAA 安装目录中的原始资源始终只读；覆盖文件执行前备份、结束后恢复或删除。若 DSH/MAA 异常中断，下次策略执行会先按恢复清单还原。
- 不新增不存在的肉鸽分组，不猜不存在的干员、藏品或事件；这些要求会从生效部分剔除，并在确认前列出原因。
- Copilot 地图不能唯一解析时，不会虚构“堵门/守蓝门”坐标；可以改用明确坐标和方向。
- MAA Copilot 是预编排动作，不是通用实时战术 AI。需要持续视觉推理、根据任意敌人状态动态改战术，或 MAA 协议没有字段承载的要求会明确回退。
- 生成策略仍需人工确认；插件不会因为本地解析或模型生成了作业就直接操作游戏。执行反馈会分别标明 MAA 日志已验证完成、明确失败，或仅确认进程结束但游戏结果仍未验证。

#### 原子化策略记忆

通过校验的自然语言策略会按最小可执行单元保存到 `~/.dsh/maa-cli/strategy-memory.json`（可随 `DSH_MAA_CLI_STATE_DIR` 改变位置）：

- 原始自然语言不会直接入库；记忆保存的是规范化后的 MAA step、肉鸽资源动作或 Copilot 动作。无法编译、资源中不存在或发生冲突的要求只进入安全回退说明，不写入记忆。依赖用户本地文件且无法稳定确认可用性的 `Custom` 任务也不持久化。
- 内置 `combat`、`roguelike`、`reclamation` 分类；其他 MAA step 会按任务类型自动形成分类。每类最多保留最近 20 条，重复语义会更新原记录和参数，不占新名额。
- 复用使用规范化动作、对象和适用场景组成的语义键，不比较用户原句，因此同义表达在模型映射到同一 MAA 动作后会命中同一条记忆，不需要额外的嵌入服务或第二次模型调用。
- 每次复用仍检查 maa-cli/MaaCore 版本、主题、地图和当前参数，并重新运行资源预览。`堵门`、`守蓝门`各只保存一条跨地图策略；记忆不保存生成坐标，每次都从当前地图重新计算。
- 同一请求中互相冲突的策略（例如同一藏品同时优先购买和禁买）都不会执行或入库。本次明确指令会覆盖相同语义的旧偏好；旧记忆按全局战术、肉鸽主题/模式、地图动作的适用范围合并。
- 记忆文件使用临时文件加原子重命名写入。版本查询或记忆写入失败时只停用本次记忆更新，不阻断原有 MAA 计划。
- 策略记忆管理面板不再显示在界面上：模型通过 `/maa strategies`、`/maa strategy-enable`、`/maa strategy-disable`、`/maa strategy-delete` 在后台查看和维护条目。禁用条目保留在文件中但不参与匹配；删除后不可恢复。

确认码规则：

- 只对**同一个 DSH 会话**有效；
- **一次性**，用过即失效；
- **30 分钟**后过期；
- DSH 重启后计划仍在磁盘上，可继续确认（默认 `~/.dsh/maa-cli/pending-plans.json`，可用 `DSH_MAA_CLI_STATE_DIR` 改目录）。

### 自动肉鸽参数面板

计划里含 `Roguelike` 步骤时，确认条和工具卡会显示「自动肉鸽参数」。主题、模式、难度、分队、职业组和开局干员不再由浏览器维护固定清单，而是从**当前实际运行的** maa-cli / MaaCore 版本及其 `resource` 目录发现；同一份能力描述同时供面板、确认参数校验和策略编译使用。黑流树海在 MaaCore 6.20.0 及以上会显示难度 0–16。

能力发现会读取肉鸽主题目录、主题任务图、`recruitment.json`、`shopping.json`、`strategy.json`、事件表和 `stages.json`。资源新增或删除主题、模式、干员、分组、藏品、事件或关卡后，能力签名随之变化；打开的确认面板每 15 秒只读刷新一次并自动换用新选项，不需要重启 DSH。切换主题时会应用该主题的默认值并清掉不适用的高级开关。

上游 Windows 包目前没有附带完整、机器可读的 MaaCore 任务参数 schema，因此以下内容仍集中在一个按版本约束的协议适配层：字段名和类型、模式中文名、推荐默认值、主题专属开关，以及 Core 内部实现但资源任务图没有节点的模式。适配层不会把未知值猜成可执行能力；资源发现结果始终优先。发现失败时沿用最近一次验证通过的 `~/.dsh/maa-cli/maa-capabilities.json`，若从未成功发现才使用最小兼容适配数据并在响应中标记警告。

基础字段包括主题、模式、难度、刷取次数、分队、职业组、开局干员和助战设置。除刷取次数外均由当前能力描述生成选项；刷取次数默认 9999，可输入 1–99999。分队、职业组和开局干员是可选参数：当前主题没有可靠选项或用户选择“未选择”时，它们会从最终 MaaCore 任务中省略，不会提交 `squad=`、`roles=` 或 `coreChar=` 空值。

难度默认是「MAX（当前最高）」：确认时按当前主题可用的难度解析成最大值（例如黑流树海解析为 16、萨卡兹为 15），避免每局手动挑难度；明确选择某个数字时仍按数字执行。

确认成功后，插件会按主题把这次的面板配置（模式、难度、刷取次数、分队、职业组、开局干员和高级开关）记到状态目录的 `panel-memory.json`；下次打开同一主题的计划时自动回填，过期的或当前能力已不再接受的值会被跳过。不同主题各自独立，Fight 等其它计划不受影响。

「高级功能（MAA 高级设置）」折叠区只显示**当前主题 / 模式下 MAA 真正会用到的开关**：切主题或换模式时，不适用的项直接不渲染、也不会随确认命令发送，避免出现「改了但 MAA 根本不理」的选项。

- 面板只提供下拉选项（开关是「是 / 否」）与刷取次数的手输数字；手工命令通道仍接受 `key=value` 文本（分队 / 职业组 / 干员长度 1–32），例如 `/maa confirm MAA-1A2B3C theme=Sarkaz mode=0 difficulty=4 useSupport=false investmentsCount=999 note=%E6%89%93%E5%AE%8C%E5%B0%B1%E5%81%9C`。

## 私有运行时

插件不打包 maa-cli、MaaCore 或资源，而是给每位用户在自己的目录里准备一份：

- **默认位置**：`~/.dsh/maa-cli/runtime`（`DSH_MAA_CLI_RUNTIME_DIR` 可改）。

- **结构**：

  ```text
  runtime/
  ├─ bin/                    maa-cli（Windows 下是 maa.exe）
  ├─ data/lib/               MaaCore 与依赖 DLL
  ├─ data/resource/          资源
  ├─ config/profiles/default.toml
  ├─ state/                  日志等
  ├─ cache/                  运行期缓存（安装包会被自动清理）
  └─ runtime.json            版本与安装信息
  ```

- **安装流程**：下载 maa-cli 官方 release（约 3.6 MB）→ `tar` 解包 → `maa-cli install --batch`（由 maa-cli 自己下载匹配的 MaaCore 与资源）→ 探测 adb 并生成 `default.toml` → 清理几百 MB 的安装缓存。

- **自动更新**：准备启动新任务时检查上次更新时间；距离上次检查满 24 小时才运行一次官方 `maa-cli update --batch`。maa-cli 自己判断远端版本，版本未变不会重复安装。更新过程全局互斥；已有任务运行时跳过，更新结束后任务才会启动。更新前用同盘硬链接保存旧 `lib`/`resource` 快照，成功后清理，失败或中断则原子恢复旧版本。

- **体积**：装完约 520–630 MB（MaaCore 约 250 MB，资源约 267 MB）。

- **隔离**：通过 `MAA_DATA_DIR` / `MAA_STATE_DIR` / `MAA_CACHE_DIR` / `MAA_CONFIG_DIR` 四个变量让 maa-cli 只认这个目录，不会读写用户全局的 MAA 配置与缓存。

- **生成任务时的目录**：先执行 `maa-cli dir config`，把任务文件写到该进程**实际使用**的配置目录，避免私有运行时与全局配置不一致。

- **卸载**：直接删除该目录即可，不影响系统里的 MAA。

- **不开 DSH 也能装**：`node scripts/install-runtime.mjs`（会打印每一步的耗时）。

- **adb 探测顺序**：`DSH_MAA_CLI_ADB_PATH` → `ANDROID_HOME` / `ANDROID_SDK_ROOT` → `%ProgramFiles%` 与各固定盘的 `Program Files` / `Program Files (x86)` 下的 MuMu / 雷电 / 蓝叠 → `PATH`。探测不到时会写出不含 `adb_path` 的 `default.toml`，手动补一行即可（地址默认 `127.0.0.1:16384`）。

## 故障排查

先跑一次体检（模型侧 `maa_doctor`）：9 项里任何一项红了，基本都能直接定位问题。

| 现象 | 原因与处理 |
| --- | --- |
| `I/O error: 系统无法将文件移到不同的磁盘驱动器。 (os error 17)` | 目标目录被 **EFS 加密**，maa-cli 的「同目录临时文件 + rename」原子写在加密目录上必然失败。把该目录 `cipher /d` 解密，或用 junction 重定向到未加密盘（`mklink /J`）。 |
| `Resource directory ... not found, ignoring` | maa-cli 回退到了内置资源，通常不影响功能；若行为异常，用 `maa_doctor` 看资源目录，再 `maa_runtime update`。 |
| 提示「请手动启动mumu模拟器！」 | 模拟器没启动或没开 ADB 调试。启动后**重新点一次确认**即可，计划不会失效。 |
| adb 连不上 / 端口不通 | `adb devices` 看设备；MuMu 需要在设置里开启 ADB，端口默认 `16384`；必要时 `adb connect 127.0.0.1:16384`。 |
| 目录一会儿存在一会儿不存在 | 从 Microsoft Store 打包的应用启动进程时，`%APPDATA%` / `%LOCALAPPDATA%` 会被重定向到 `%LOCALAPPDATA%\Packages\<包名>\LocalCache\{Roaming,Local}`，且「写后才物化」。插件用 `paths.js` 在两个视图里查找，`maa_doctor` 会显示实际路径。 |
| 运行时下载慢或失败 | 设置 `DSH_MAA_CLI_ASSET_URL` 指向镜像/离线 zip，或手动下载后放到 `runtime/downloads/` 再重试 `install`。 |
| 提示「当前 DSH 会话已有一个 MAA 任务正在执行」 | 同一会话同时只能跑一个任务；先 `/maa stop` 或等它结束。 |
| 提示「MAA 任务正在执行中（…）」 | 有任务在跑时所有新计划都会被拒绝（跨会话共享）；在面板点「停止任务」或输入 `/maa stop`。 |
| 面板显示「最近一次 MAA 执行」 | 这是持久化的执行记录；点「×」隐藏，需要时通过 `/maa status` 重新读取。运行中的面板可点「查看实时进度」。 |
| 确认按钮点了没反应 / 提示确认码不匹配 | 确认码单会话、一次性、30 分钟过期；重新让模型准备一次计划即可。 |
| 任务跑到第 5 分钟就停 / 报 `This operation was aborted` | 旧版把整次 MAA 执行放在一次命令调用里，被命令传输的 5 分钟超时打断。新版已改为后台执行：确认后立刻返回「已开始执行」，MAA 进程独立持有到退出；如果仍看到，说明 DSH 还在跑旧插件代码，重启 DSH Desktop 生效。 |

## 安全边界

- 只调用 maa-cli 的**白名单**子命令（查询类 `version` / `help` / `list` / `dir`，执行类 `run`），并对参数做字符校验；不会执行任意 shell。
- 只操作游戏：不涉及充值、不修改账号资料、不改动系统 MAA 的配置。
- 停止操作只对**本插件当前运行记录对应的进程树**执行 `taskkill /T`；DSH 重启后的兜底清理也只匹配 `dsh-generated`，不会波及其它 MAA 实例、游戏或模拟器。
- 确认码机制保证「模型提议」与「用户批准」是两次独立动作。

| `src/capabilities/` | MAA 版本/资源能力发现、签名缓存与协议版本适配 |
| `src/commands/` | 本地命令解析、MaaCore 任务规划与确认码管理 |
| `src/runtime/` | maa-cli 调用、私有运行时、路径、状态、模拟器预检与环境诊断 |
| `src/operators/` | 干员 Box 缓存与培养建议 |
| `src/strategy/` | 自然语言策略的严格校验、原子化记忆、肉鸽资源事务覆盖与 Copilot 作业生成 |
| `test/` | 全部 Node 测试，包括统一零模型参数面板用例 |
| `config/` | DSH/Cordis 插件挂载配置 |
| `scripts/` | 不启动 DSH 时可独立运行的维护脚本 |
| `docs/` | 开发与交接文档 |
| `artifacts/` | 本地历史打包文件；不随 npm 包发布 |

测试统一放在 `test/`，全部走 `node --test test/*.test.mjs`，无第三方依赖。

发布流程：

```bash
# 1. 改 package.json 的 version
npm test
npm publish                       # 2. 发布到 npm
git tag -a v<version> -m "<说明>"  # 3. 打 tag
git push origin main --tags       # 4. 推送并创建 GitHub Release
```

## 常见问题

**需要先装 MAA 吗？**
不需要。插件会自己准备运行时；系统里已有的 MAA 也不会被影响。

**会覆盖我现有的 MAA 配置吗？**
不会。所有读写都限制在私有运行时目录内，通过四个 `MAA_*_DIR` 环境变量隔离。

**装了插件以后原来的 MAA 还能用吗？**
能。两者互不干扰。

**为什么不把 MAA 打包进 npm 包？**
MaaCore 与资源有几百 MB，且 MAA 采用 AGPL-3.0，重新分发需要承担相应的源码义务。按需下载更轻，也更容易跟随上游更新。

**支持哪些服？**
Official、Bilibili、Txwy（台服）、YoStarEN/JP/KR。用自然语言指定即可，例如「日服刷 1-7 两次」。

**能一次刷 100 次以上吗？**
单条命令上限 100；需要更多可以分多次执行。

**任务跑到一半能暂停吗？**
MaaCore 没有可靠的暂停/继续接口；可以立即停止，或让插件根据可靠回调在本局结算、再完成 N 局、指定层 Boss 前终止。停止后不会自动补完剩余局数。

**日志在哪里？**
私有运行时下的 `state/debug/`；也可以用 `maa_query` 的 `log_dir` 查询实际路径。
